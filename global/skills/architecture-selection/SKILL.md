# 成熟架构选择器

## 核心目标
把"模型每次现场发明架构"换成"从成熟目录里选 + 显式记录决策"。每次新项目跑 `/vibe-plan` 时，本 skill 对 NFR 适用的维度弹选项（含推荐与优劣），用户选定后写 ADR，落到 `docs/02-ARCHITECTURE.md`。

## 元原则（必须遵守）

1. **从目录选，不现场发明** — 模型训练默认值 = 隐性架构决策（vibe architecting），须显式对抗：任何选型必须能指向本目录的某个选项。
2. **fit-driven** — 复杂度匹配问题，拒绝 over-engineering。小型本地工具不该上 K8s + 微服务。
3. **默认选成熟可验证** — PostgreSQL > 自研存储，12-Factor > 自造轮子，GitHub Actions > 手写脚本。
4. **每维必须给答案** — 选模式 + 一句话理由，或**显式"不适用(理由)"**。禁止静默跳过（静默 = 模型默认值替用户做决定）。
5. **每决策记 ADR** — Context/Decision/Alternatives/Consequences/Verification，写 `docs/05-DECISIONS.md`。
6. **推荐度 ⭐ = 业界默认** — 用户回车即接受；只有偏离默认时才需要思考。

## 交互式选型流程（由 /vibe-plan 的架构选型步骤触发）

```
1. 读 docs/01-PRD.md §3 NFR（规模/SLO/数据量/并发/合规/RTO·RPO）
2. 遍历 10 维，逐维判定适用性：
   - NFR 涉及该维 → 用 question 工具弹选项（选项 label 带 ⭐推荐 + 一句话优劣）
   - 不涉及 → 直接记 "不适用(理由)"
   - 单用户本地工具默认只有 2-3 维适用（如 前端/后端/数据库），其余全部"不适用"
3. 每个用户选择 → 写一条 ADR 到 docs/05-DECISIONS.md
4. 汇总为 docs/02-ARCHITECTURE.md §9 选型表（一行一维）
5. 若 G05 门禁存在：保证 §9 每维"有决策 或 显式不适用"
```

question 工具呈现格式（每个选项 description 含优劣，推荐排第一）：
```
「维度: 数据库」选择数据库引擎:
- PostgreSQL⭐ (推荐: ACID完整+生态成熟+JSON/向量扩展；劣势: 单机写吞吐有上限，连接开销需池化)
- MySQL (劣势: 无原生JSON索引、锁粒度粗；适用: 已有MySQL运维经验)
- MongoDB (适用: 文档模型/灵活schema；劣势: 跨文档事务贵、关系查询弱)
- SQLite (适用: 单机/嵌入式；劣势: 无网络并发)
```

## 10 维选型目录

### D1 架构风格
| 选项 | 适合 | 不适合 | 优劣 | 可验证方式 | 推荐度 |
|---|---|---|---|---|---|
| Modular Monolith（模块化单体） | 绝大多数中小型应用、团队 <20 人 | 已明确多团队独立部署需求 | + 简单可靠、事务跨模块天然支持、无网络开销；- 规模后单库瓶颈 | 模块边界测试（禁止跨模块 import） | ⭐ |
| Hexagonal（端口-适配器） | 需替换外部依赖（DB/HTTP/队列）的场景 | 一次性原型 | + 可测试性、依赖倒置；- 抽象层多、样板代码 | 用 mock 适配器跑核心逻辑测试 | 备选 |
| Clean Architecture | 业务规则复杂、需长期演进 | 小型 CRUD | + 领域隔离；- 分层样板多，AI 容易过度抽象 | 依赖方向规则检查 | 特定场景 |
| Microservices | 团队大、独立部署/独立伸缩需求明确 | 小团队、单体可撑 | + 独立扩展故障隔离；- 分布式事务、运维爆炸、调试难 | 契约测试+混沌演练 | 特定场景 |
| Serverless | 突发流量、事件驱动、无运维意愿 | 长连接/常驻进程/低延迟敏感 | + 免运维自动扩缩；- 冷启动、供应商锁定 | 压测冷启动+成本核算 | 特定场景 |

### D2 前端/客户端
| 选项 | 适合 | 不适合 | 优劣 | 可验证方式 | 推荐度 |
|---|---|---|---|---|---|
| Next.js (React) | 需要 SEO/SSR 的 Web 应用 | 纯客户端工具 | + 生态最大、RSC/缓存新特性；- 版本迭代快、概念多 | E2E + 性能预算 | ⭐ |
| Vue / Nuxt | 团队熟悉 Vue、中小型 Web | 重度 SSR 需求 | + 上手平缓、中文资料多；- 生态略小于 React | E2E | 备选 |
| Flutter | 跨平台移动端/桌面，UI 一致性要求高 | 纯 Web（无移动需求） | + 单代码库多端、渲染一致、性能好；- 包体大、Web 支持弱于原生框架 | 真机/模拟器 E2E + 截图对比 | 移动端 ⭐ |
| React Native | 已有 React 团队、要移动端 | 复杂动画/原生深度集成 | + 复用 React 技能；- 桥接层调试难 | 真机 E2E | 移动端备选 |
| Svelte / SvelteKit | 小型应用、追求编译时优化 | 大型团队生态依赖 | + 代码少、无虚拟 DOM；- 生态较小 | E2E | 特定场景 |
| 原生小程序 (WX) | 目标平台是微信生态 | 多端需求 | + 微信流量直达；- 锁定微信、多端需重写 | 小程序真机预览 | 特定场景 |

### D3 后端
| 选项 | 适合 | 不适合 | 优劣 | 可验证方式 | 推荐度 |
|---|---|---|---|---|---|
| Node.js (NestJS/Express/Fastify) | 全栈 JS 团队、I/O 密集 | CPU 密集计算 | + 前后端同语言、生态大；- CPU 密集无优势、回调心智负担 | 压测 + 集成测试 | ⭐ |
| Python (FastAPI/Django) | AI/数据处理、快速原型 | 高并发 I/O 或 CPU 密集生产 | + 开发快、AI 生态最强；- 性能弱于 Go/Rust、部署需 ASGI | 压测 + 类型检查 | AI 场景 ⭐ |
| Go (Gin/Echo) | 高并发 API、云原生基础设施 | 快速原型、业务 CRUD 迭代 | + 性能好、并发原语强、部署单二进制；- 样板多、泛型弱 | 压测 + race detector | 高并发 ⭐ |
| Java (Spring Boot) | 企业级、团队有 JVM 经验 | 快速迭代的轻量项目 | + 生态最全、稳定；- 启动慢、内存高、开发重 | 集成测试 + 压测 | 特定场景 |
| Rust (Axum) | 性能/内存敏感、系统级 | 业务快速迭代 | + 极致性能、内存安全；- 学习曲线陡、开发慢 | 压测 + cargo clippy | 特定场景 |

### D4 数据库
| 选项 | 适合 | 不适合 | 优劣 | 可验证方式 | 推荐度 |
|---|---|---|---|---|---|
| PostgreSQL | OLTP 关系数据、需事务/复杂查询/JSON/向量 | 超高吞吐写、访问模式固定 | + ACID 完整、生态成熟、扩展丰富(pgvector)；- 连接开销大需池化、单机写上限 | 迁移测试+恢复演练+压测 | ⭐ |
| MySQL | 已有 MySQL 运维经验 | 需 JSON 索引/复杂窗口函数 | + 生态成熟；- 锁粒度粗、JSON 支持弱 | 压测 | 备选 |
| SQLite | 单机/嵌入式/原型 | 网络并发多写 | + 零运维、零配置；- 单写者、无网络访问 | 单元测试 | 轻量 ⭐ |
| MongoDB | 文档模型、schema 灵活 | 强事务、复杂 join | + 水平扩展易；- 跨文档事务贵、关系弱 | 数据一致性测试 | 特定场景 |
| Redis | 缓存/会话/计数（见 D5） | 持久化主存储 | + 极速；- 内存成本、持久化弱 | 压测 + 重启数据校验 | 缓存 ⭐ |
| ClickHouse | OLAP 列式分析 | 事务性 OLTP | + 列式聚合极快；- 非事务、更新弱 | 查询性能基准 | 分析场景 |
| 向量库 (pgvector/Qdrant) | 语义搜索/RAG | 常规 CRUD | + 语义检索；- 规模大需专门引擎 | 召回率评测 | AI 场景 |

### D5 缓存/内存管理
| 选项 | 适合 | 不适合 | 优劣 | 可验证方式 | 推荐度 |
|---|---|---|---|---|---|
| Redis cache-aside | 读多写少、缓存热点 | 数据强一致要求 | + 命中率提升显著；- 缓存穿透/雪崩需防护 | 命中率监控 + 穿透测试 | ⭐ |
| Memcached | 极简 KV 缓存、多实例 | 需数据结构/持久化 | + 更简单更快；- 功能少 | 命中率监控 | 备选 |
| 进程内缓存 (LRU) | 单实例、启动慢数据 | 多实例一致性 | + 零网络延迟；- 实例间不一致 | 压测 | 轻量 |
| 连接/线程池预算 | 任何有 DB/HTTP 的服务器 | 无并发 | + 防连接耗尽(OOM/拒连)；- 需调参 | 压测观察连接数 | 必选 ⭐ |
| 流式/分批处理 | 大文件/大数据集 | 小数据 | + 内存占用恒定；- 代码复杂 | 内存监控(heap/RSS) | 大数据 |

### D6 高并发
| 选项 | 适合 | 不适合 | 优劣 | 可验证方式 | 推荐度 |
|---|---|---|---|---|---|
| 无状态水平扩展 | 需横向扩容的服务 | 状态密集(如聊天室) | + 加实例即扩容；- 状态外置(DB/Redis)是前提 | 多实例压测 | ⭐ |
| 异步 worker 队列 (BullMQ/Celery) | 慢任务(邮件/图片处理) | 实时响应需求 | + 主请求快速返回；- 队列消费延迟/失败重试需管理 | 队列积压监控 + 失败重试测试 | ⭐ |
| 令牌桶限流 | 防滥用/保护下游 | 无外部依赖 | + 简单有效；- 需定阈值 | 压测超阈值观察 429 | 必选 ⭐ |
| 熔断器 (Circuit Breaker) | 依赖外部服务 | 无外部调用 | + 防止级联故障；- 误熔断需调参 | 故障注入测试 | 外部依赖必选 |
| 幂等键 | 重试安全的写操作 | 只读接口 | + 防重复提交；- 需存键值 | 重复请求幂等测试 | 必选 ⭐ |
| K8s | 规模化多服务 | 单机/小集群 | + 自愈/自动扩缩；- 运维复杂度爆炸 | 滚动发布 + 故障演练 | 规模化 |

### D7 事务与锁
| 选项 | 适合 | 不适合 | 优劣 | 可验证方式 | 推荐度 |
|---|---|---|---|---|---|
| READ COMMITTED + 乐观锁(version) | 绝大多数 OLTP | 高争用写热点 | + 默认隔离够用、乐观锁无锁等待；- 冲突时重试开销 | 并发写入冲突测试 | ⭐ |
| 悲观锁 (SELECT FOR UPDATE) | 高冲突写、库存类 | 读多写少 | + 确定性；- 锁等待/死锁风险 | 死锁检测 + 压测 | 特定场景 |
| SAGA（分布式事务） | 跨服务最终一致 | 单库事务即可 | + 不锁长事务；- 补偿逻辑复杂、调试难 | 故障注入 + 补偿演练 | 微服务必选 |
| Outbox 模式 | 本地事务+发消息一致性 | 无消息依赖 | + 保证"写库即发消息"原子；- 需清理表 | 消息不丢失/不重复测试 | 微服务推荐 |
| 幂等键 | 支付/下单等重复敏感操作 | 只读 | + 防重复扣款；- 需幂等存储 | 重复请求幂等测试 | 必选 ⭐ |

### D8 CICD
| 选项 | 适合 | 不适合 | 优劣 | 可验证方式 | 推荐度 |
|---|---|---|---|---|---|
| GitHub Actions | GitHub 托管、个人/小团队 | 企业私有云隔离要求 | + 零运维、市场丰富；- 私有仓库分钟数限制 | 流水线跑通 + 门禁生效 | ⭐ |
| GitLab CI | 自托管/GitLab 用户 | 无 GitLab | + 自托管自由；- Runner 运维 | 流水线跑通 | 备选 |
| 流水线阶段 | 任何项目 | 无 | lint→typecheck→test→安全扫描→构建→部署 | 每阶段 gate 阻断 | 必选 ⭐ |
| 环境晋升 (dev→staging→prod) | 有部署场景 | 纯本地工具 | + 问题早暴露；- 环境维护成本 | 各环境验证记录 | 部署必选 |
| 蓝绿 / 金丝雀部署 | 服务可回滚 | 单机 | + 零停机/灰度；- 需双份资源 | 回滚演练 + 灰度流量观察 | 部署 ⭐ |
| Trunk-based 分支 | 单人/小团队高频合并 | 大团队需长命分支 | + 减少合并地狱；- 需小步提交纪律 | PR 门禁检查 | ⭐ |

### D9 灾备 (DR)
| 选项 | 适合 | 不适合 | 优劣 | 可验证方式 | 推荐度 |
|---|---|---|---|---|---|
| 3-2-1 备份 + 定期恢复演练 | 任何有数据的系统 | 无数据/纯原型 | + 3份副本2介质1异地；- 存储成本 | 定期 restore 测试（关键！） | 必选 ⭐ |
| RTO/RPO 前置定义 | 有 SLA 的系统 | 本地工具 | + 明确恢复目标；- 需权衡成本 | 演练实测 RTO/RPO | 必选 ⭐ |
| 主备 / 多活 (Patroni/云托管 HA) | 需要高可用 | 可接受停机 | + 自动故障切换；- 双份成本、脑裂风险 | 主节点故障演练 | 高可用 ⭐ |
| 跨区域复制 | 多地域/灾难级 | 单地域即可 | + 地理容灾；- 跨区延迟/成本 | 区域故障演练 | 大规模 |
| Git 即代码灾备 | 所有项目 | 无 | + 代码天然多副本可回滚；- 不含数据/配置 | 从 clone 恢复 | 必选 ⭐ |

### D10 部署/运行
| 选项 | 适合 | 不适合 | 优劣 | 可验证方式 | 推荐度 |
|---|---|---|---|---|---|
| Docker 单容器 | 任何可容器化应用 | 无部署需求 | + 环境一致、易迁移；- 单点 | 构建+启动冒烟 | 必选 ⭐ |
| Docker Compose | 多服务本地/单机 | 生产规模 | + 一条命令起全套；- 无自动扩缩 | compose up 冒烟 | 中小项目 ⭐ |
| K8s | 规模化生产 | 小项目 | + 编排/自愈/扩缩；- 运维重 | 滚动发布演练 | 规模化 |
| 云托管 (Railway/Fly/云厂商) | 不想运维 | 成本敏感/数据合规 | + 免运维自动伸缩；- 锁定、成本 | 部署+监控 | 快速上线 ⭐ |
| 自托管 (VPS) | 数据主权/成本控制 | 无运维能力 | + 完全掌控；- 运维负担、故障自扛 | 部署+监控+备份演练 | 特定场景 |

## 引用成熟框架
- **12-Factor**（12factor.net）— 配置外置/后端服务即资源/进程无状态/开发生产对等
- **AWS Well-Architected** 6 支柱 — Operational Excellence / Security / Reliability / Performance Efficiency / Cost Optimization / Sustainability
- **ADR**（Michael Nygard）— Context/Decision/Alternatives/Consequences
- **CAP / PACELC** — 分布式存储一致性/可用性权衡
- **SRE**（Google）— SLO/错误预算/容量规划

## 常见反模式（AI 容易犯，须拦截）
- 无理由上微服务（单体足够时）
- 自研轮子替代成熟库（zod/ORM/缓存库）
- schema 未定就选 NoSQL
- 无并发需求却上 K8s
- 有数据却无备份/恢复演练
- 分布式事务用 2PC 而非 SAGA/outbox
