# PRD 生成器

## 核心目标
将用户的原始需求转化为结构化、可验证的 PRD 文档，输出到 `docs/01-PRD.md`

## 输入
- 用户的原始需求描述（自然语言、对话记录）
- 已有项目背景（如果有）

## 输出
- `docs/01-PRD.md` — 完整 PRD 文档
- 每个功能块包含验收标准

## 工作步骤

### Step 1: 需求拆解
- 将原始需求拆成功能模块
- 每个模块一个 H2 标题
- 分辨核心功能和边缘功能

### Step 2: 补验收标准
对每个功能模块，补以下问题：
- 什么算"做完"？
- 成功路径是什么？
- 失败路径是什么？（失败提示文案、多次尝试后是否锁定、超时处理）
- 边界条件是什么？（空数据、极端输入、并发）
- 成功后跳转到哪里？

### Step 3: 视觉框架
- 找 2-3 个参考网站 / 风格方向
- 定导航结构（顶部/侧边/无）
- 定页面布局
- 排除 AI 味词汇："智能"、"赋能"、"助力"、"驱动"、"生态"

### Step 4: 项目边界
回答三个问题写入 PRD：
1. 本地自用还是上线公开？
2. 有无用户数据、支付、隐私合规需求？
3. 性能和成本上限？

### Step 5: 非功能需求（NFR）——架构选型的输入依据
量化写死，不写"高性能/高可用"这类空词。每项必须给数值或明确"不适用(理由)"：
- 预期规模：用户量 / 数据量（当前 + 3 年）/ QPS
- 可用性目标：SLO（如 99.9%），能否接受停机
- 并发上限：峰值在线数 / 写并发
- 数据一致性：强一致 / 最终一致，能否接受脏读
- 合规：隐私 / 等保 / GDPR / 支付合规
- 灾备：RTO / RPO 要求，是否需要异地
- 部署环境：本地 / 云 / 客户现场（决定 Docker/K8s/单机）
- 团队技能：熟悉的技术栈（选型要贴合，避免为用而用）
